# Data Model (ARCH-003, ADR-007)

Status: **APPROVED** 2026-10-27 by the user (DR-003 → ADR-007). Implemented in `src/server/db/schema.ts` and `drizzle/` (DB-001).
Based on `docs/SPEC.md` §8, §11, §16, §33 and ADR-002/004/006.

## Conventions
- PostgreSQL 16, snake_case tables, plural names.
- Primary keys: `uuid` (v7 generated in app, time-ordered). No sequential IDs are ever exposed publicly.
- Every operational row carries `branch_id` (and `restaurant_id` on top-level rows) for future multi-branch (ADR-002). One restaurant + one branch are seeded at launch.
- Money: `bigint` minor units (`*_minor`) + `currency char(3)` on financial rows (ADR-006). No floats anywhere.
- Time: `timestamptz` in UTC. `business_date date` computed with the branch timezone at write time.
- Status columns: Postgres `text` + `CHECK` constraint (easier to evolve than enums).
- Optimistic concurrency: `version int` on rows with state machines (`table_sessions`, `orders`).
- No hard deletes on anything referenced by history; use `is_active` / `archived_at`.
- Translatable text: `name_ar`, `name_en`, `description_ar`, `description_en` columns (two languages only, per spec). Fallback language is a setting.

## Key integrity rules
1. Order creation = one transaction: lock/create the open session for the table, allocate seq, insert order + items + modifiers + event, store idempotency result. `NOTIFY` is sent after commit.
2. Prices and totals are always recomputed on the server from current `products`/`modifier_options`; the client sends only IDs, quantities and notes.
3. Rounding: tax computed per order on the taxable subtotal, rounded half-up to the minor unit (documented in `money.ts`).
4. Session close: `UPDATE … WHERE id = $1 AND version = $2` + check no order is unpaid (unless cancelled) or READY-but-undelivered; second concurrent closer gets a conflict error.
5. Table identity on public endpoints comes only from `qr_token`, never from a table number in the request.

## Indexes (beyond PK/unique)
- `orders (branch_id, business_date)`, `orders (session_id)`, `orders (branch_id, kitchen_status) WHERE kitchen_status IN ('NEW','ACCEPTED','IN_PREPARATION','READY')`
- `order_items (order_id)`, `order_events (order_id, created_at)`
- `assistance_requests (branch_id, status)`, `payments (order_id)`, `audit_logs (entity_type, entity_id)`, `audit_logs (created_at)`

## Choices approved with ADR-007
1. UUID v7 primary keys (generated in the app).
2. Two fixed language columns (`*_ar`, `*_en`), no translations table.
3. Fixed role→permission map in code (DR-004); permissions table only if custom roles are needed later.
4. One `order_events` table for kitchen, delivery and payment history.
